# 提案書: 非エンジニアが安全に Claude Code を使うためのハーネス設計

> 事務職レベル（プログラミングの専門知識がない）の人が Claude Code（cc）で
> 「自分用のアプリを作る」「ファイルを整える」などをやっても、
> ①壊さない・漏らさない、②知識がなくても要件以外はエージェント側が固める、
> ③使うほど賢くなる、を満たすハーネスの設計提案。

## 0. エグゼクティブサマリ

非エンジニアが cc を使うときに起きる事故は、技術力の不足そのものより
**「危険なことをしているのに気づけない」「何を決めればいいか分からない」「同じ失敗を繰り返す」**
の 3 つのギャップから生まれる。本提案はこれを 3 本柱で塞ぐ。

| 柱 | 守るもの | 中心的な仕掛け |
|---|---|---|
| **A. 安全ガードレール** | 壊さない・漏らさない | 権限 3 層（allow/ask/deny）+ PreToolUse フックによる実行時ブロック + 作業ディレクトリ隔離 + 監査ログ |
| **B. 要件補完** | 知識がなくても進められる | 着手前の「1 枚仕様（spec-lite）」合意 + 非機能要件のデフォルト注入 + 平易な言葉での確認・報告 |
| **C. 自己改善** | 同じ失敗を繰り返さない | 既存の記憶/knowhow ループ + セッション後のふりかえり + 訂正・誤検知の取り込み |

重要な前提: **CLAUDE.md は「お願い」であって強制力がない**（モデルはユーザー指示で上書きしうる）。
だから安全はドキュメントではなく **フックと権限という強制レイヤ**で担保する。これが設計の背骨。

このワードローブには既に多くの土台（allowlist 方式の権限、メモリ MCP、knowhow システム、
レビューサブエージェント、各種フック）が揃っている。本提案は**作り直すのではなく、
既存の土台に「非エンジニア向けの強制レイヤと補完レイヤ」を足す**方針をとる。

## 1. 背景と課題

### 1.1 想定ユーザーとユースケース

- **誰**: 事務職レベル。Excel やブラウザは使えるが、ターミナル・Git・プログラミングは未経験。
- **何をしたい**: 「経費の集計アプリを自分用に作りたい」「散らかったフォルダを整理したい」
  「議事録を決まった形式に変換したい」「簡単な Web ページを作りたい」など。
- **期待**: 要件（やりたいこと）だけ伝えれば、残りはエージェントが安全に固めてくれる。

### 1.2 3 つのギャップ

| ギャップ | 具体例 | 放置するとどうなるか |
|---|---|---|
| **安全性ギャップ** | `rm -rf`、秘密鍵の読み取り、`git push --force`、`curl \| bash` の意味を理解できない | ファイル消失、情報漏洩、取り返しのつかない外部操作 |
| **要件ギャップ** | 「集計アプリ作って」だけで、保存形式・エラー時の挙動・バックアップを決められない | 動くが使い物にならない／壊れやすい成果物 |
| **学習ギャップ** | 同じ指摘を毎回しないと直らない、好みが蓄積されない | 体験が一向に良くならない、信頼が育たない |

### 1.3 設計の難所

- cc はユーザーと同じ権限でシェルを動かせる。攻撃対象領域が広い（`.env`・SSH 鍵・任意の bash）。
- ガードレールを厳しくしすぎると「何も作れない」、緩めすぎると「事故る」。**可逆な操作は自由に、
  不可逆・外部影響のある操作だけ止める**バランスが要。
- 非エンジニアは確認プロンプトの意味を判断できない。だから「ユーザーに無限に聞く」のは解にならない。
  **エージェントが安全側に倒して自分で固め、判断が必要なときだけ平易に聞く**設計にする。

## 2. 設計原則

1. **強制は仕組みで、助言はドキュメントで。** 安全はフック＋権限で強制し、CLAUDE.md は意図の共有に使う。
2. **Allowlist を土台に、deny を上塗り（ゼロトラスト）。** 既定は読み取りのみ。deny は allow/ask に優先する。
3. **可逆を既定に。** 破壊的・不可逆操作（削除・上書き・force push・外部送信）は止めるか、必ずバックアップ／確認を挟む。
4. **要件以外はエージェントが固める。** 非機能要件（保存形式・エラー処理・バックアップ・可搬性）は
   既定値を持ち、ユーザーに丸投げしない。
5. **聞くのは"決め"だけ、平易な言葉で。** 専門用語を投げない。選択肢は 2〜3 個に絞り、推奨を添える。
6. **使うほど賢く。** 失敗・訂正・好みを記憶し、次回の既定に反映する。ガードレール自体も誤検知から学習する。
7. **多層防御。** 1 つのレイヤが破れても次が止める（権限 → フック → サンドボックス → 監査ログ）。
8. **レベルに合わせる。** 言葉の平易さ・自動で決める範囲・説明の量・確認の頻度を、ユーザーの技術レベルに応じて変える。
   レベルは初期セットアップで確認し、いつでも変えられる。
9. **「開ける」形で届ける。** 非エンジニアにとって最も親切な成果物は ①URL ②ダブルクリックで開ける HTML。
   「`npm start` してください」で終わらせない。動かすのにひと手間要るものは、ボタン 1 つ／URL で動く形まで仕上げる。

## 3. 三本柱の設計

### 柱A — 安全ガードレール（壊さない・漏らさない）

#### A-1. 権限の 3 層化（allow / ask / deny）

現状は allow リストのみ。ここに **ask（実行前に確認）と deny（常に拒否）** を足し、ゼロトラスト化する。

- **allow（確認なしで実行）**: 読み取り系・可逆な編集・`bun`・`git`（push を除く）・承認済み MCP。
- **ask（実行前にユーザー確認）**: `git push`、デプロイ、パッケージのインストール、新規ディレクトリ外への書き込み。
- **deny（常に拒否）**: 秘密情報の読み取り（`.env`・`secrets/**`・SSH 鍵）、`rm -rf` 系、`curl|bash`、
  任意のリモートシェル、`enableAllProjectMcpServers`。

deny は allow より強い、という Claude Code の評価順序を利用する。詳細スニペットは §4.1。

#### A-2. PreToolUse フックによる実行時ガード（最重要）

権限リストは「コマンド種別」単位でしか効かない。`Bash(git:*)` を許すと `git push --force` も通る。
そこで **PreToolUse フックで実際のコマンド文字列を検査**し、危険パターンを exit code 2 でブロックする
（stderr のメッセージがモデルにフィードバックされ、安全な代替に切り替わる）。

ブロック対象（例）:
- `rm -rf`、`rm` でホームや親ディレクトリを指すもの、`find ... -delete`
- `git push --force` / `git reset --hard` / `git clean -fdx`
- `chmod 777`、`sudo`、`chown`
- パイプ to シェル（`curl ... | sh`、`wget ... | bash`）
- 作業ディレクトリの**外**への書き込み（`/etc`、`~/.ssh`、システム領域）

「止める」だけでなく **「なぜ止めたか」を非エンジニアにも分かる日本語で**返すのがポイント。

#### A-3. 作業ディレクトリの隔離（サンドボックス）

- 非エンジニアの作業は専用の `~/cc-workspace/<プロジェクト名>/` に閉じ込める。
- ファイル書き込み・削除はこのディレクトリ配下のみ allow、外は deny。
- OS レベルのサンドボックス（Claude Code 公式のサンドボックス機能）が使える環境では併用する。
  公式実績で確認プロンプトを 84% 削減しつつ安全性を上げられる＝**安全と使いやすさを両立**できる。

#### A-4. 秘密情報の保護

- `Read(./.env)`・`Read(**/secrets/**)`・`Read(~/.ssh/**)` を deny。
- 出力に資格情報・APIキー・個人情報（メール・電話・マイナンバー形式）が混じったら
  PostToolUse／Stop フックで検出・マスクする（簡易 PII フィルタ）。

#### A-5. 外部送信は必ず一拍おく

- `git push`・デプロイ・`WebFetch`／外部 POST は ask（確認）に。
- 「これは外（インターネット／他人が見える場所）に出ます」と**影響範囲を明示**してから確認する。
  外部送信は取り消せない（キャッシュ・インデックスされうる）ため、ここは譲らない。

#### A-6. 監査ログ

- PostToolUse フックで「いつ・どのツールで・何をしたか」を `~/cc-workspace/.audit/log.jsonl` に追記。
- 事故時の追跡、自己改善（柱C）の入力、ユーザーへの「何をしたかの説明」に使う。

### 柱B — 要件補完（知識がなくても、あなたが固める）

> 思想: ユーザーが言うのは**要件（What/Why）**だけでいい。
> **How と非機能（どう作る・どう守る）はエージェントが既定で固める。**
> これは Spec-Driven Development の考え方を非エンジニア向けに薄くしたもの。

#### B-0. ユーザーレベル・プロファイル（初期セットアップで確認）

すべての補完・説明・確認の振る舞いは、**ユーザーの技術レベル**に応じて変える。
レベルは `/wd-setup` の初回（または `/wd-level` でいつでも）に、**専門用語を使わない平易な質問**で確認し、
`~/.claude/cc-profile.json` に保存する。本人の自己申告 + 会話からの推定（自己改善で更新）を併用する。

| レベル | 目安 | 言葉の平易化 | 自動で決める範囲 | 確認の頻度 | 専門用語 |
|---|---|---|---|---|---|
| **L1 事務職・未経験** | ターミナル/Git 未経験 | 最大（全部かみ砕く） | 最大（要件以外は全部こちら） | 最小（決めだけ・2〜3択） | 使わない／必ず言い換え |
| **L2 すこし分かる** | Excel関数・簡単な設定はできる | 中（要所を補足） | 中（重要な技術選択は提示） | 中 | 括弧で補足 |
| **L3 ある程度わかる** | 多少のコード・CLI 経験あり | 小（必要時のみ） | 小（選択肢を出して任せる） | 通常 | そのまま使う |

- このプロファイルが**柱B 全体（B-1〜B-6）と柱A の確認文言・柱C の報告**のトーンを一括で制御する。
- 「今のは難しかった」「もっと任せたい」等の発言で**その場で調整**し、プロファイルに反映（柱C-3）。
- 設計上の単一スイッチにすることで、一貫した体験になる（ある画面だけ急に専門的、を防ぐ）。

#### B-1. 着手前の「1 枚仕様（spec-lite）」合意 — md + HTML + 使い方マニュアル

少しでも規模のある依頼（アプリ・複数ファイル操作）では、コードを書く前に **1 枚の要約**を作って合意する。
**文字だけだとアプリ仕様は伝わりにくい**ため、Markdown だけでなく **HTML 版も出力**し、
ワイヤーフレーム／画面イメージ／フロー図（簡単な図）を添えて、見て分かる形にする。

```
■ 作るもの：経費集計アプリ（自分用）
■ 使う場面：月末に、ダウンロードした明細CSVを読み込んで合計を出す
■ 入力／出力：input/ に置いた CSV → 集計結果を result.xlsx に
■ できたと言える条件：手元のサンプルCSVで正しい合計が出て、エラーでも落ちない
■ やらないこと：他人と共有する機能、クラウド保存（今回は対象外）
■ こちらで決めた前提：保存形式は Excel、元データは消さずコピーして処理、失敗時は元に戻す
```

- 専門用語を使わず、**ユーザーが読んで Yes/No を言えるレベル**にする。
- 「こちらで決めた前提」を明示することで、ユーザーは**要件以外を考えなくていい**ことが伝わる。
- 合意できたら memory に保存（柱C の入力になる）。

**出力形式と「開き方」の案内（レベル別）:**
- `spec.md`（編集・差分用）と `spec.html`（閲覧用、図つき）の**両方**を生成。
- L1/L2 には**開き方を具体的に**添える: 「`spec.html` を**ダブルクリック**するとブラウザで開きます」。
  ファイルの場所も平易に示す（「デスクトップの〇〇フォルダの中」）。
- 仕様だけでなく、完成後は **使い方マニュアル（`manual.html` / `manual.md`）もセットで生成**する。
  - 内容: 「これは何か」「使う前の準備」「手順（スクショ or 図つき）」「困ったとき」。
  - L1 向けは**操作手順を 1 ステップずつ画像/図**で。文章だけにしない。
  - マニュアルは成果物に**必ず同梱**（README より手前の、初見の人向けドキュメント）。

#### B-2. 非機能要件のデフォルト注入

ユーザーが指定しなくても、エージェントが既定で満たす項目（プロジェクト類型ごとにテンプレ化）:

| 観点 | 既定の振る舞い |
|---|---|
| **データ保護** | 元データは絶対に上書きしない。必ずコピーして処理。処理前に自動バックアップ。 |
| **エラー処理** | 落ちる前に分かりやすいメッセージ。途中失敗は「元に戻す」を既定に。 |
| **保存形式** | 事務職が開ける形式（.xlsx / .csv / .pdf / .docx）を優先。独自形式は避ける。 |
| **可搬性** | ダブルクリックや 1 コマンドで動く。複雑な環境構築を要求しない。 |
| **説明可能性** | README を平易な日本語で同梱。「使い方」を 3 行で。 |
| **再実行性** | 何度実行しても壊れない（冪等）。 |

#### B-3. 安全なプロジェクトテンプレート（類型別 scaffold）

よくあるユースケースを類型化し、足回り（フォルダ構成・バックアップ・README・.gitignore）を
**最初から正しい形**で用意する。ユーザーは要件を埋めるだけ。

- 「データを集計・変換する」型（CSV/Excel → 集計）
- 「ファイルを整理する」型（リネーム・仕分け、**コピー先で作業し原本は触らない**）
- 「簡単な Web ページ／自分用ツール」型（単一フォルダで完結、外部送信なし）

#### B-4. 平易な言葉での確認・報告（専門用語の翻訳）

- 確認は `AskUserQuestion` で 2〜3 択、**推奨に「おすすめ」を付ける**。専門用語は避けるか括弧で補足。
- 作業報告は「やったこと・できた結果・次にできること」を箇条書きで。エラーログをそのまま貼らない。
- 「コミット」「ブランチ」等の語は、必要なときだけ「（＝作業の保存）」のように言い換える。

#### B-5. 成果物の配置場所（テンプレート配布と両立する設計）

このワードローブは**パブリックテンプレートとして配布**され、本家（embodied-claude-wardrobe）と
配布先リポジトリの間で `/wd-migrate` による同期が走る。**ユーザーが作った成果物がテンプレートの
バージョン管理対象パスに混ざると、同期時にマージ衝突を起こす。** これを避ける配置ルールを既定にする。

| 配置 | 場所 | マージ安全性 | 既定 |
|---|---|---|---|
| **リポジトリ外**（推奨） | `~/cc-workspace/<app名>/` | テンプレートと完全分離。衝突しない | ◎ 既定 |
| **リポジトリ内（要時）** | リポジトリ直下の `workspace/`（`.gitignore` 済み） | 追跡対象外なので衝突しない | ○ 必要時 |
| テンプレート追跡パス内 | `.claude/` や `docs/` 配下 | **衝突する。禁止** | ✗ |

- 既定は**リポジトリ外の `~/cc-workspace/`**。これは柱A-3 のサンドボックス境界とも一致する（一石二鳥）。
- 成果物を Git 管理したい場合は、**成果物専用の別リポジトリ**を作る（テンプレートと混ぜない）。
- `/wd-migrate` の保護対象リスト・`.gitignore` に `workspace/` と `cc-profile.json` 等を追加し、
  **配布テンプレートの差分にユーザー固有物が乗らない**ことを保証する。

#### B-6. 成果物の届け方とデプロイ既定（ランタイム別 × レベル別）

> **核心: 「どう動かすか（ランタイム）」と「ユーザーレベル」で既定を決め、平易に説明して選ばせる。**
> 静的 HTML はダブルクリックで開けるが、Node 等のサーバ実行が要るアプリは
> 「起動する」概念自体が非エンジニアには難しい。だから**成果物の型に応じて届け方を変える**。

着手時（spec-lite の段階）に、作るものを**動かし方の難易度で分類**し、届け方の既定を決める:

| アプリの型 | 例 | 非エンジニアの起動難易度 | 既定の届け方（レベル別） |
|---|---|---|---|
| **静的（開くだけ）** | 単一HTML/CSS/JS、集計結果ファイル | 易（ダブルクリック） | **ローカルで完結**。`index.html` をダブルクリックで開ける形に仕上げる |
| **要ランタイム（起動が必要）** | Node/Python のローカルサーバ、要ビルド | 難（コマンド起動が要る） | ①**起動を 1 アクション化**（`start.command`/`start.bat` の用意）か、②**ホスティングして URL を渡す**ことを優先 |
| **動的・常時稼働** | DB やログイン付き、外部API | 最難 | **ホスティングして URL を渡す**を既定（手元で起動し続けるのは非現実的） |

**デプロイ既定（プライベートリポジトリ前提・選択可能）:**

ユーザーの回答どおり、デプロイも**レベルに合わせて説明しつつ選べる**ようにする。既定の推奨は次の通り:

1. **まずローカル完結を試す。** 静的にできるなら静的にして、ダブルクリックで開ける形を最優先（最も親切・無料・公開リスクなし）。
2. **共有・公開が必要 or 要ランタイムなら、選択肢を平易に提示して選んでもらう:**
   - **GitHub Pages（推奨デフォルト）** — 静的サイト向け。テンプレート本体はプライベートのまま、
     **成果物専用のパブリックリポジトリを別途作成して登録**し、ビルド成果物だけを公開。URL を渡す。
   - **Vercel / Netlify 等の外部ホスティング** — 要ランタイム/動的機能向け。
     アカウント連携が要る点を**平易に説明**し、必要なら案内（この環境では Vercel 系 MCP が使える場合がある）。
   - **ローカルのまま（起動スクリプト同梱）** — 公開したくない/個人利用のみのとき。
3. **どれを選ぶかの説明はレベル別に変える。** L1 には
   「これは“ダブルクリックで開ける”やつ／これは“ネットに置いてURLで開く”やつ」程度のかみ砕きで提示し、
   `node を実行` のような概念は前面に出さない。L3 には構成をそのまま見せる。
4. 公開を伴う操作（パブリックリポジトリ作成・push・デプロイ）は**柱A-5 の「外部送信は一拍おく」確認**を必ず通す。

**デプロイ既定構成のまとめ:** 「ローカル完結を基本に、必要時だけ GitHub Pages 用の**別パブリックリポジトリ**、
動的なものは外部ホスティング」を既定とし、いずれも**ユーザーレベルに応じた説明つきで選択可能**にする。

### 柱C — 自己改善（作業と応答から学ぶ）

> 既存資産が強い領域。**memory-mcp・knowhow・レビューサブエージェント**が既にある。
> ここに「ふりかえりの定着」と「ガードレールの学習」を足して回す。

#### C-1. 既存ループの活用

- **記憶**: 判断の分岐点・感情・失敗・ユーザーとの合意を memory に保存（CLAUDE.md の記憶プロトコル準拠）。
- **knowhow**: 再利用可能な実装知見・落とし穴は `docs/knowhow/` に蓄積（`/wd-knowhow`）。
- **想起**: 着手前に FLASH.md→`search_memories` で「この人の好み・過去の前提」を引く。

#### C-2. セッション後のふりかえり（Reflexion）

セッション終了時（BOOT_SHUTDOWN.md の日記手順に統合）に、構造化された自己点検を行う:

- 何がうまくいき、何でつまずいたか
- ユーザーに訂正された点（＝次回の既定にすべき好み）
- ブロックされた操作・誤検知（＝柱A のルール改善候補）

Reflexion の要点は「**失敗の要約を明示的にメモリへ保存し、次の類似タスクで retrieval する**」こと。
これは既存の記憶システムでそのまま実現できる。

#### C-3. ユーザーフィードバックの即時取り込み

- ユーザーが「そうじゃなくて」「いつもこうして」と言ったら、その場で memory に好みとして記録し、
  以降の既定（柱B のデフォルト）に反映する。
- 「ありがとう、これでいい」等の肯定も、成功パターンとして弱く記録する。

#### C-4. レビューサブエージェントによる自己点検

- 既存の `wd-code-review`／`wd-doc-review` を、成果物を渡す前のセルフチェックに使う。
- 非エンジニアは品質を判断できないので、**エージェントが自分でレビューしてから渡す**のが安全。

#### C-5. ガードレール自身の改善ループ

- ブロック／誤検知のログ（A-6 の監査ログ＋C-2 のふりかえり）を週次でレビューし、
  「止めるべきだったのに通した」「止めすぎて不便」をルール改善案として提示する。
- ルール変更は人間（あなた）の承認を挟む。**ガードレールがガードレールを勝手に緩めない**のが鉄則
  （自己改善が安全性を侵食しないための歯止め）。

## 4. 具体的な実装提案（差分）

> すべて既存ファイルへの追記・新規追加。破壊的変更なし。スニペットは方向性を示すもので、
> 実装時に環境変数・パスを合わせる。

### 4.1 `.claude/settings.json` — 権限 3 層

```jsonc
"permissions": {
  "allow": [
    "Read", "Glob", "Grep",
    "Edit", "Write",                         // 後述の deny で作業ディレクトリ外を遮断
    "Bash(bun run:*)", "Bash(bun:*)",
    "Bash(git add:*)", "Bash(git commit:*)", "Bash(git status:*)", "Bash(git diff:*)",
    "mcp__memory__*"
  ],
  "ask": [
    "Bash(git push:*)",
    "Bash(npm install:*)", "Bash(bun add:*)", "Bash(pip install:*)",
    "WebFetch"
  ],
  "deny": [
    "Read(./.env)", "Read(**/.env)", "Read(**/secrets/**)", "Read(~/.ssh/**)",
    "Bash(rm -rf:*)", "Bash(sudo:*)", "Bash(chmod 777:*)",
    "Bash(git push --force:*)", "Bash(git reset --hard:*)", "Bash(git clean:*)",
    "Write(/etc/**)", "Write(~/.ssh/**)", "Edit(/etc/**)"
  ]
}
```

### 4.2 新規フック `.claude/hooks/guard-pretool.sh`（PreToolUse）

- 役割: Bash コマンド文字列と書き込み先パスを検査し、危険パターンを exit 2 でブロック。
- 検査: §A-2 の危険パターン＋「作業ディレクトリ外への書き込み」。
- 返却: ブロック時は stderr に**平易な日本語の理由＋安全な代替案**を出す。
- `settings.json` の `hooks.PreToolUse` に matcher `Bash|Write|Edit` で登録。

### 4.3 新規フック `.claude/hooks/audit-log.sh`（PostToolUse）

- 役割: ツール名・要約・タイムスタンプを `~/cc-workspace/.audit/log.jsonl` に追記。
- 副次効果なし（読み書きのみ）。タイムアウト 5s。

### 4.4 新規スキル `/wd-spec`（1 枚仕様の作成・合意）

- 入力: ユーザーのざっくりした依頼。
- 出力: §B-1 の 1 枚仕様を **`spec.md` と `spec.html`（図つき）の両方**で生成。
  着手時に**アプリの型（静的／要ランタイム／動的）を分類**し、届け方の既定もここで決める（§B-6）。
- `AskUserQuestion` で不明点だけ平易に確認 → 合意 → memory 保存。
- L1/L2 には `spec.html` の**開き方（ダブルクリック）と場所**を添える。
- 規模のある依頼で着手前に自動的に提案する（フックで誘導してもよい）。

### 4.5 新規スキル `/wd-scaffold`（安全テンプレート展開）

- 類型を選び、`~/cc-workspace/<name>/`（テンプレート追跡外＝マージ安全, §B-5）に
  正しい足回り（README・**使い方マニュアル `manual.html`**・バックアップ・.gitignore）を展開。

### 4.6 新規スキル `/wd-plain`（成果の平易な報告）

- 直近の作業を「やったこと・結果・次にできること」の 3 ブロックで日本語要約。専門用語を翻訳。
- 報告のトーンは `cc-profile.json` のレベルに従う（§B-0）。

### 4.9 新規スキル `/wd-level`＋プロファイル（§B-0）

- 初回 `/wd-setup` 内で技術レベルを**平易な質問**で確認し、`~/.claude/cc-profile.json` に保存。
- `/wd-level` でいつでも変更可。会話からの推定で自己更新（柱C-3）。
- このプロファイルを各スキル・フックが参照し、平易化・自動決定範囲・確認頻度を一括制御。

### 4.10 新規スキル `/wd-deploy`（届け方の決定と実行, §B-6）

- アプリの型 × レベルから**届け方の既定を提示**（ローカル完結／GitHub Pages 別パブリックリポジトリ／外部ホスティング）。
- 選択肢を**レベル別の言葉**で説明（L1 は「ダブルクリックで開く／URLで開く」程度）。
- 公開を伴う操作は柱A-5 の確認を通す。要ランタイムは起動スクリプト（`start.command`/`start.bat`）も生成。

### 4.11 `/wd-migrate` 保護リスト・`.gitignore` への追記（§B-5）

- `workspace/`・`~/.claude/cc-profile.json`・`.audit/` を保護対象／無視対象に追加。
- **配布テンプレートの差分にユーザー固有物・成果物が乗らない**ことを保証し、本家↔配布先の同期を衝突なく保つ。

### 4.7 新規ドキュメント `SAFETY.md`

- 何を止める／止めない、なぜそうするかの一覧。CLAUDE.md から参照。
- 非エンジニア向けの「困ったときは」も併記。

### 4.8 既存ドキュメントへの追記

- **CLAUDE.md**: 「非エンジニア安全モード」の節を追加し、柱B/C の振る舞いを行動規範として明文化。
- **BOOT_SHUTDOWN.md**: 日記手順に C-2（ふりかえり）の構造化項目を追加。

## 6. リスク・残課題・運用上の注意

- **ガードレールは完全ではない。** パターンマッチは回避されうる。多層防御（権限＋フック＋サンドボックス）と、
  最終的には**信頼できる作業ディレクトリ・できればコンテナ/VM**で外堀を埋める前提。
- **過剰ブロックの不便。** 誤検知は C-5 のループで継続的に緩める。ただし緩和は人間承認必須。
- **「自分用アプリ」の配布は別問題。** 他人に渡す・公開する段階では、本提案の範囲を超えた
  セキュリティレビューが要る。`/wd-spec` の「やらないこと」で線引きを明示する。
- **非機能デフォルトの押し付けすぎ注意。** 「こちらで決めた前提」は必ず可視化し、ユーザーが覆せるようにする。
- **PII フィルタは簡易。** 完全な DLP ではない。重要情報を扱う場合は事前にユーザーへ注意喚起する。
- **レベル推定は外れる。** 自動推定は誤りうる。常に**安全側（より平易・より自動）に倒し**、ユーザーがいつでも `/wd-level` で上書きできるようにする。
- **パブリック公開は不可逆。** GitHub Pages 用パブリックリポジトリへの push は「世界中から見える」状態を作る。
  L1/L2 には**この意味を平易に説明**してから（柱A-5）実行し、機密が含まれないことを確認する。成果物リポジトリは必ずテンプレートと別にする。
